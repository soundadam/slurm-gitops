# ADR-0001 控制器放在 aalab 内网的一台非 GPU 主机上

## 背景

`114.212.224.242` 是 aalab 的 NAT 出口：它的 `100NN` 端口转发到 gNN 的 SSH，别的端口不开，
节点出网也显示为这个地址。它上面跑不了 slurmctld。

slurmctld 与 slurmd 是双向通信的。节点要连控制器的 6817，控制器也要主动连每台节点的 6818；
`srun` 还要求节点能连回提交机的临时端口。

## 决定

**D1** slurmctld、slurmdbd 和 MariaDB 放在 `192.168.50.0/24` 里的同一台控制主机上，这台主机不做 GPU 计算节点。

**D2** 候选按顺序是：
1. 实验室现有的常开服务器，比如 NIS/NFS 所在的 `192.168.50.229`，前提是管理员同意；
2. 在内网单独开一台小虚拟机或小主机；
3. 最后的退路是一台 GPU 节点，但它要从 `gpu` 分区里去掉。

**D3** 在 elon 上跑的控制器只用于测试（见 rollout 第 1 阶段），不承担实验室的正式调度。

## 理由

- 放在内网里，各节点之间直接互通，不需要为每台节点在 NAT 上单独开 6818 转发。
- GPU 节点会因为升级驱动而重启，也会被用户进程压满内存。控制器放在上面，
  它的状态目录和调度就会跟着一起受影响。
- NIS/NFS 服务器本来就是全实验室的单点：它停了，大家都登不上去。控制器和它放在同一台，
  不会新增一个故障点。

## 什么时候重看

控制主机定下来以后，把 D2 改成那台主机的名字。如果实验室把网络重组成多个网段，或者要做 slurmctld 的主备，也要重看这份 ADR。
