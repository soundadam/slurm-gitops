# 方案：计算与存储分离

数据集中放到存储节点上，GPU 节点的本地盘只当缓存。要买的东西逐项见[采购需求单](purchase.md)，两台存储各自怎么配见[热存储](hot-storage.md)和[冷存储](cold-storage.md)，身份与控制节点单独见 [control-and-identity](control-and-identity.md)，整改的步骤和停机时间见 [software](software.md)。

## 范围

- **一步到位做计算与存储分离，** 热存储、冷存储、网络一起买。
  - 只买冷存储、不买热存储的中间做法不采用：冷存储是机械盘，随机读太慢，训练数据还得拷回本地盘，本地盘就擦不掉，数据照样锁在单机上。
  - 这样也省掉了中间做法里的汇聚交换机，网络一次按最终的样子买。
- **不做异地副本。** 它防的是整个机房出事，这次不在范围里。不可再生的数据（原始录音、人工标注）用两块离线备份盘兜底，见[冷存储「RAID 不是备份」](cold-storage.md#raid-不是备份)。
- **Slurm 这一轮不上。** 成员的用法这一轮不变。存储的路径、网络和身份都按以后要接 Slurm 来设计，接的时候不用再返工，见 [software](software.md)。

## 拓扑

```text
                      100G 核心交换机
     │100G         │25G          │25G ×2       │10G 电口 ×2   │10G
  热存储 st1     冷存储 st0     g18  g19       g8  g9       2.5G 接入交换机
  /home                                                     │2.5G
  /project                                              台式机 13 台

  现有千兆交换机：SSH、BMC、NAT 出网，保持不变
  两台管理机：接在千兆交换机上，改作控制节点
```

| 层级 | 给谁 | 速率 | 为什么 |
| --- | --- | --- | --- |
| 存储节点 | 热存储 st1 | 100G | 所有节点同时读数据，压力都在这里 |
| | 冷存储 st0 | 25G | 机械盘阵列本身写入约 1 GB/s，25G 够用 |
| 大 GPU 节点 | g18、g19，以及以后新买的 8 卡机 | 25G | 卡多，读数据的量大；这两台现在只有千兆口，要加装网卡 |
| | g8、g9 | 10G | 已经有 10GBASE-T 电口，直接用 |
| 台式机 | 其余节点 | 2.5G | 消费级卡训练吞吐有限，2.5G（约 280 MB/s）一般够用；八台的板载网卡已经支持 2.5G，只要换交换机 |
| 管理网 | 所有节点的 SSH 和 BMC | 1G | 沿用现有交换机 |

- **数据网单独一个网段，** 只走 NFS 和数据复制，不设网关、不出网。SSH 和出网还走原来的千兆网，NAT 的端口转发不用动。
- **台式机只有一个网口，** 所以台式机的数据网和管理网走同一根线，用 VLAN 分开。服务器有多余的网口，两张网各走各的。
- **不用 InfiniBand：** 训练几乎都是单机，GeForce 卡也不支持 GPUDirect RDMA。

## 数据放在哪

| 路径 | 放什么 | 在哪 | 规则 |
| --- | --- | --- | --- |
| `/home/nis/<用户>` | 代码、环境、配置 | 热存储 | 路径和现在一样；每人设配额，每小时快照 |
| `/project/<组>` | 正在用的数据集、checkpoint、实验产物 | 热存储 | 按组设配额，每小时快照，每天复制到冷存储 |
| `/project/shared` | 多人共用的公开数据集 | 热存储 | 管理员保管，成员只读，一份就够 |
| `/scratch` | 训练时的本地缓存 | 各 GPU 节点自己的固态盘 | 自动清理，不备份，丢了从热存储重新拷 |
| `/cold` | 全部现有数据的冻结副本、归档、热存储的备份 | 冷存储 | 只读挂载；归档打成 tar 放进来 |

**冷存储不给训练直接按条读。** 一组 raidz2 做随机读，只有一块盘的能力，每秒一两百次。文件平均 0.5 MB 的话，全实验室一起读，合计只有一两百 MB/s。正在用的数据要放在热存储上。

## 热存储带来什么变化

对成员来说，这是这次整改里变化最大的一件事。

| 事情 | 现在 | 有了热存储以后 |
| --- | --- | --- |
| 数据在哪 | 某台节点的 `/data/ssdN/<用户>/` | `/project/<组>/`，每台节点上路径都一样 |
| 换一台机器跑 | 先走千兆网拷数据，几小时到几天 | 直接跑 |
| 读训练数据 | 读本地盘 | 25G 的服务器直接读 `/project`，约 2.8 GB/s，比节点自己的 SATA 盘还快；台式机读大文件或打包好的 shard 直接读，零碎的小文件先拷到 `/scratch` 再读 |
| 本地盘 | 放正本，满了找人删 | 当 `/scratch` 缓存，定期清理 |
| 误删 | 找不回来 | 自己进 `.zfs/snapshot/` 拿回任意一个整点的版本 |
| 盘坏了 | 那块盘上的数据没了 | 热存储能同时坏两块盘，冷存储上还有一份 |
| 家目录 | 在 229 上，走千兆，虚拟环境 import 慢 | 在热存储的固态盘上，走 2.5G 以上，路径不变 |
| 公开数据集 | 好几个人各拷一份 | `/project/shared` 里放一份 |
| 空间 | 没有配额，盘满了才知道 | 每组有配额，`df` 就能看到还剩多少 |
| 谁看得到我的数据 | 只有能登录那台机器的人 | 所有节点都挂载，靠文件权限和组来管 |
| docker | g5、g19 上直接用 | 容器里的 root 写不进 NFS，要用 `--user` 跑，或者换 Apptainer |
| 不用了的数据 | 留在本地盘上占地方 | 打成 tar 挪到冷存储 |

**成员要改的习惯只有三件：**
1. 数据的路径从 `/data/...` 换成 `/project/<组>/...`。
2. 本地盘是缓存，不放唯一的一份。
3. 共享以后要在意文件权限：别人的组能不能读，由你目录的权限决定。

**代价：**
- **热存储是单点。** 它停了，所有节点都读不到数据，要等修好。数据丢不了：热存储每天把快照复制到冷存储，整台坏了，最多丢最近一天的改动。
- **台式机读大量小文件比本地盘慢。** 2.5G 的网再加上每个文件一次网络往返，小文件多的数据集要先拷到 `/scratch`，或者打包成 shard。
- **要有组。** 现在 NIS 里只有两个组，按组分配额和权限之前要先建组，见 [control-and-identity](control-and-identity.md)。

## 日常训练怎么跑

**一次训练用到的东西各放在哪：**

| 东西 | 放在哪 | 为什么 |
| --- | --- | --- |
| 代码 | 家目录下的 git 仓库 | 小，每小时有快照 |
| Python 环境 | 每个项目自己的 `.venv`，用 uv 建，放在项目目录里 | 按锁文件 `uv sync` 就能重建，环境本身不用备份 |
| uv 的缓存 | 保持默认的 `~/.cache/uv` | uv 从缓存用硬链接装包，缓存和 `.venv` 要在同一个文件系统上；把缓存挪到 `/scratch`，uv 就退回逐个复制，又慢又占空间。缓存会越攒越大，定期 `uv cache prune` |
| 数据集 | `/project/<组>/datasets/<名字>@<版本>/`，做好以后只读 | 不再改的数据集才能放心地缓存到 `/scratch`、给多人共用 |
| 训练时读的数据 | 大文件和打包好的 shard 直接读 `/project`；零碎的小文件先 rsync 到 `/scratch/<用户>/` | 见上一节 |
| checkpoint、日志、TensorBoard | `/project/<组>/runs/<实验>/` | 要保住，所以不放 `/scratch`；家目录有配额，也不放大文件 |
| 临时文件 | `/scratch` 或 `/tmp` | 不备份，随时会被清 |

**训练脚本的几条写法。** 现在就能照着写，以后接 Slurm 也不用改：
- **路径不写死机器名和 `/data/ssdN`。** 数据和输出的根目录从环境变量或配置里读，换机器、换存储只改一处。
- **不写死卡号。** 用哪几张卡由外面的 `CUDA_VISIBLE_DEVICES` 决定。现在自己设；接 Slurm 以后由 Slurm 设，只露出分给这个作业的卡。
- **能断点续训。** 定期存 checkpoint，启动时自动接上最近的一个。接 Slurm 以后单个作业有时长上限，用空闲卡的作业会被卡的主人挤掉、重新排队，能续训就不白跑。
- **每次跑用自己的输出目录，** 按实验名和时间分开。几个跑同时往一个目录里写同名文件，在 NFS 上会互相覆盖。
- **启动命令写进一个脚本，** 参数、环境变量都在里面。现在用 `nohup` 跑它；接 Slurm 以后把同一个脚本交给 `sbatch`。
- **要用容器就用 Apptainer。** 镜像是一个文件，放在 `/project` 上所有节点都能用，里面以自己的身份运行，读写 NFS 没有权限问题。

**交互开发照旧：** VS Code 的 Remote-SSH 照常连节点，看到的家目录和 `/project` 和别的节点一样。接 Slurm 以后，先申请到卡再连过去。

## 还不解决

- **所有副本都在同一个机房。**
- **热存储坏了要停一阵。** 数据在冷存储上有一份，丢不了，但恢复要时间。
