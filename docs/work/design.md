# 集群设计

这是一份工作中的设计，不是定稿。飞书上给同事看的现状、方案、采购单都在 `docs/ref/`，入口是
[ref/README.md](../ref/README.md)；这里只放倾向、判断的理由、不适合放到飞书上的采购细节和待定问题，
不重复 ref 里的事实。现有数据怎么搬见 [migration.md](migration.md)，还缺哪些动作见 [rollout.md](rollout.md)。

## 1. 现状与目标

现状见 [current](../ref/current.md)，要解决什么、目标拓扑见 [ref/README](../ref/README.md)，范围见 [plan「范围」](../ref/plan.md#范围)。

## 2. 为什么直接做计算与存储分离

- **只有冷存储的中间做法推不动整改。** 冷存储随机读只有一块盘的能力，数据还得拷回本地盘训练，本地盘就擦不掉，
  成员也没有动力把数据交出去。中间做法里的汇聚交换机到最后还是多余的。
- **异地副本是黑天鹅，先搁着。** 不可再生的数据用两块离线 16T 盘兜底；超过 16T 再说。
- **不只用本地缓存、不要中心热存储的做法也不采用：** 缓存背后的正本在冷存储上，缓存没命中时一样是机械盘随机读；
  而且缓存在哪台机器上，作业又开始跟着机器走。

## 3. 网络

**倾向：**
- **核心交换机倾向 MikroTik CRS520-4XS-16XQ。** 两个 10G 电口正好接 g8、g9，省两个电口模块；
  RouterOS 一个人配得动；风扇比机房淘汰的 32 口 100G 交换机安静。预算紧才换现货 SN2700 或 7060CX：
  它们要装 Onyx、Cumulus 或 SONiC，配置和排错都更费事，噪音也只能放机房。
- **更省的一档是 MikroTik CRS504-4XQ（4 口 100G）。** 热存储一口、拆 4×25G 一口（冷存储、g18、g19）、
  拆 4×10G 一口（g8、g9 要电口模块、接入交换机上联），刚好够，没有余量，热存储也只有一个 100G。只在预算被砍时拿出来。
- **数据网单独一个没有网关的网段**，比如 `10.50.0.0/24`；NFS 只在它上面导出。IP 规划和 VLAN 要管理员一起定。
- **MTU 先保持 1500。** Realtek 8125、I225 和 25G 口混在一起，巨帧一处配错，NFS 会卡住而不报错。
  稳定以后再只在 25G 那一段试 9000。
- 13 台台式机 × 2.5G = 32.5G，接入交换机上联 2×10G；瓶颈本来就在存储的口上，这个收敛比可以接受。

## 4. 存储

**倾向：ZFS + NFS。** 快照、压缩、校验都是自带的，`zfs send` 就能复制到另一台，一个人能运维。
备选是 BeeGFS 或 CephFS：能横向扩展，但运维重得多，等存储节点超过三台、或者单台带宽顶到上限了再考虑。

- **热存储起步 8 块盘。** 6 块要成员先挑数据，挑的过程会拖慢第 5 步；多花的 ¥1.6–3 万换这个不值得省。
  价格回落前不补到 12 块。
- **热、冷存储合成一台不采用。** 能省一套机箱、CPU、内存和一个网卡，约 ¥1–5 万；
  但热存储每天备份到的就是同一台机器，机器坏了正本和备份一起停，备份也就不独立了。
- **NFS 挂载：** 所有节点用 autofs 挂 `/project`、`/cold`，家目录保持 `/etc/fstab` 挂 `/home/nis`，只改服务器地址。
  客户端用 `nconnect=8`，单个客户端在 25G 上才跑得满。导出用 `sec=sys`、`root_squash`，只对数据网网段。
- **本地缓存的做法：** 倾向「作业开头 rsync 到 `/scratch/<用户>/<数据集>@<版本>`」，不开 fscache。
  fscache 只缓存数据不缓存元数据，打开每个小文件照样要问一次服务器，对 0.5 MB 的 wav 帮助有限。
  缓存默认数据集不可变（带版本的目录），这样缓存不用管失效。
- **「冷存储只收 tar」只管冻结以后成员主动放进去的归档。** 冻结进去的那一批原样只读，
  随宽限期结束由主人删或挪走，不重新打包；热存储复制过来的备份是 `zfs send` 流，不按文件访问，也不受这条约束。
- **冷存储要 special vdev**，理由在 [cold-storage](../ref/cold-storage.md#池怎么排)；建池前用 g18 的一块盘实测一次元数据量再定盘的大小。
- **建池时就定、以后改不了的：** `ashift=12`、`xattr=sa`、`acltype=posixacl`；冻结用的 dataset `recordsize=1M`；
  `compression=lz4`；冷存储 `atime=off`。

## 5. 身份与登录

**倾向：FreeIPA，但不急，排在控制节点到位之后。** 选项和对照见 [control-and-identity](../ref/control-and-identity.md)。

- **收益是中等的，不是显著的。** 实测 NIS 里不带口令（口令字段都是 `x`，没有 shadow 表），
  所以「NIS 泄露口令哈希」这条最常见的理由在这里不成立。真正的收益是组能管、登录和 sudo 能集中配、
  登录不依赖家目录的 NFS、身份服务有两份。热存储按组分配额这件事，是促使它这一轮就做的原因。
- **FreeIPA 服务端不在 Ubuntu 上跑。** 控制节点装 Rocky 或 Alma，或者在 Ubuntu 上跑官方的 freeipa-container。
  两者之间倾向直接装 Rocky：容器方案升级和排错都多一层。节点侧只装 client 和 SSSD。
- **NFS 不上 Kerberos。** 训练跑几天票据会过期；公钥登录的会话里本来也没有票据。
- **uid 和 gid 原样迁移**（比如 tianchi.liu 仍然是 1165）。
- 管理员要是不愿意多维护一套 RHEL 系的机器，退路是 OpenLDAP 加 SSSD 加 LDAP Account Manager，功能够用，按主机限制登录要自己拼。

## 6. 控制节点

要求见 [control-and-identity](../ref/control-and-identity.md#控制节点)。

- **家目录放在热存储上，不放在控制节点上。** 家目录真正需要的是「坏了能恢复」，快照复制比两台机器之间做 NFS 高可用简单得多。
- **倾向先看现有两台管理机能不能直接当控制节点。** 能用就省一笔；不能用就买两台现货 1U。
- **elon 上的测试控制器**在控制节点到位后退出，elon 最多保留提交机的身份。

## 7. Slurm

这一节的数都是开跑时的初值，由实验室成员商量后调整。

### 组件

- 全集群所有节点跑同一个 Slurm 版本，用上游 tarball 自带的 `debian/` 自己打包，
  22.04 和 20.04 各出一套，都带 NVML 插件。升级顺序是 slurmdbd → slurmctld → slurmd → 客户端。
- 开 configless 模式：只有控制节点上有 `slurm.conf`，计算节点只需要知道控制器地址。
- munge key 全集群共用一把，时钟由 chrony 同步。

### 分区与 GPU

GPU 用 GRES 声明（`AutoDetect=nvml`），型号作为 type，比如 `3080ti`、`3090`、`4090`、`5880ada`；
显存档位写成 Feature，比如 `vram12g`、`vram24g`、`vram48g`。

| 分区 | 用途 | 抢占 |
| --- | --- | --- |
| `gpu`（默认） | 日常训练 | 不被抢 |
| `debug` | 调试、交互 | 不被抢，优先级最高 |
| `scavenge` | 用空闲卡跑可中断的作业 | 被其他分区抢占，抢占后重新排队 |
| `own-<组>` | 某个组出资购买的节点 | 抢占 `scavenge` |

- 用 `select/cons_tres` 分开记账 CPU、内存和 GPU。`DefCpuPerGPU`、`DefMemPerGPU` 按节点组分别设：
  台式机是 12–24 线程配 2 卡，g18 是 208 线程配 8 卡，比例差得太多，不能用一个值。
- Slurm 最小只能按整台节点划分，没法把单独某几张卡划给某个人。
  所以卡的归属改成节点主人享有优先权：主人的作业走 `own-<组>` 分区；其他人只能用 `scavenge` 借这台节点的空闲卡，主人的作业一来，借用的作业就被挤掉、重新排队。

### QOS 与优先级

按公平份额排队（`priority/multifactor`），历史用量的半衰期为 7 天。

| QOS | 单作业最长 | 每人同时占用 | 备注 |
| --- | --- | --- | --- |
| `normal` | 3 天 | 8 卡 | 默认 |
| `debug` | 4 小时 | 1 卡，1 个作业 | 优先级加成 |
| `long` | 14 天 | 2 卡 | 按人授予 |
| `scavenge` | 3 天 | 不限 | 可被抢占 |

### 权限

- **身份**：Slurm 不另建用户，直接用目录服务里的 uid（见第 5 节）。
- **账户树**：slurmdbd 里「account（组）→ user」两级，开启
  `AccountingStorageEnforce=associations,limits,qos,safe`，没被加进任何组的人提交不了作业。
  账户树、各人的 QOS、各组的份额在本仓用声明式文件写，脚本只把差异通过 `sacctmgr` 应用上去，改权限走 PR。
- **管理角色**：

| 角色 | 谁 | 能做什么 |
| --- | --- | --- |
| Slurm 管理员 | 你和实验室管理员 | 改配置、改账户、操作任何作业 |
| 协管员（Operator） | 每组一人 | hold/release、requeue、把节点置为 drain/resume |
| 组协调人（coordinator） | 组负责人 | 在本组内加人删人、调组内限额 |
| 普通成员 | 其他所有人 | 提交、查看、取消自己的作业 |

  sudo 只给要在节点上装包、改系统文件的人，日常调度管理都不需要 root。
- **节点上的执行边界**：
  - cgroup v2 限制设备、CPU 和内存，作业只看得到分给它的卡。
  - pam_slurm_adopt（`PrologFlags=contain`）：在一台节点上没有作业的人 ssh 不进去；有作业的人 ssh 进去后，会话被收进那个作业里。
    管理员组不受限制。sshd 的 PAM 栈里要去掉 `pam_systemd`。
  - docker 组等于 root，能绕开所有限制。接入 Slurm 的节点上，容器改用 Apptainer。
    目前哪些节点装了 docker，见 inventory 的「系统与软件」。

### 按整节点、分阶段接入

一台节点要么完全由 Slurm 管，要么完全不接入。同一张卡上如果既有调度分配的作业、又有绕过调度直接跑的进程，
调度出来的分配就不可信。按整节点接入也方便逐台回退。
先接大节点（卡多，调度的好处最明显），再接台式机。

## 8. 成员的日常作业流

| 场景 | 以前 | 用 Slurm 之后 |
| --- | --- | --- |
| 跑一次训练 | ssh 到节点，看 `nvidia-smi` 找空卡，`nohup python ...` | 在登录节点 `sbatch train.sh`，脚本里写 `#SBATCH --gres=gpu:1` |
| 挑型号或显存 | 自己记住哪台节点是什么卡 | `--gres=gpu:4090:2` 或 `--constraint=vram48g` |
| 调参扫描 | 手写循环，自己轮流分卡 | `sbatch --array=0-19%4` |
| 交互调试 | 直接 ssh 进节点 | `srun -p debug --gres=gpu:1 --pty bash` |
| VS Code / Jupyter | Remote-SSH 直接连节点 | 先 `salloc -p debug ...`，再 Remote-SSH 连分到的节点 |
| 看队列、看用量 | 在群里问 | `squeue --me`、`sacct`、`sshare` |

这套流程适合实验室日常使用。代价是：交互使用要先 `salloc`（高优先级的 `debug` 分区让这一步几乎不用排队）；
用 docker 的人要改用 Apptainer。数据仍锁在本地盘上的作业只能绑定到那台节点，要等第 4 节的存储落地才能解开。

## 9. 采购

逐项的规格和价格见 [purchase](../ref/purchase.md)。下面是不放到飞书上的考虑。

- **分两批下单。** 网络、冷存储、控制节点、UPS 先买：价格相对稳，而且冻结要先有冷存储和网络。
  热存储的 U.2 最后买，下单前再询一轮价；企业级固态最近一个月还涨了一成多。
- **现货去哪买：** 国内做机房拆机的服务器商家，或者闲鱼上走担保交易的。
  交换机、网卡、准系统能拿到的价格常常是全新的两到三成。到货以后当场验：交换机开机看端口全亮、网卡刷固件跑一次 iperf、
  准系统跑一晚内存测试。
- **拆机 U.2 的价格按批次差很多。** 拿到报价就要序列号，看 SMART 里的写入量、剩余寿命和通电时长。
  剩余寿命低于九成的不要；同一批里不同通电时长的混着买，免得同一时间一起老化。
- **价格来源：** 企业级固态和服务器内存的涨幅来自 2026 年各家渠道的报价与行情跟踪；MikroTik 交换机按海外零售价折算；
  机房淘汰的 100G 交换机按二手市场挂价。都要在下单前重新询价。
