# 集群设计

这是一份工作中的设计，不是定稿。每一节写清现状、可选方案和目前的倾向；
标着「待定」的，要等调查或讨论后再定。硬件的数字都在 [inventory.md](../ref/inventory.md)，
这里只引用结论，不重复抄数。按预算分几档怎么买见 [tiers.md](../ref/tiers.md)，
现有数据怎么搬走见 [migration.md](migration.md)，还缺哪些动作见 [rollout.md](rollout.md)。

## 1. 现状

- **网络是一台交换机加一个 NAT。** 节点都在 `192.168.50.0/24`。对外只有 `114.212.224.242`：
  它把 `100NN` 端口转发到 gNN 的 SSH，别的端口不开，节点出网也显示为这个地址。
  g12–g14 走另一个出口 `210.28.136.239`，从 elon 连不上。
- **数据网是千兆。** 除了 g8、g9 各有一个 10G 口，其余节点都只有 1G 连接。其中八台台式机的网卡本身支持 2.5G，是被交换机压成了 1G。
  1G 实际能跑约 110 MB/s，搬 1 TB 要两个半小时以上。
- **数据分散在各节点的本地盘上。** 按介质、按节点的用量见 inventory 的「存储资源」，大多数盘都快满了。
  唯一的共享存储是 `192.168.50.229` 上的 home。
  数据和产物在哪台机器上，作业就只能在哪台机器上跑；要换机器，就得走千兆网慢慢搬。
- **大多数节点是台式机。** 17 台里只有 4 台是带 BMC 的服务器（g8、g9、g18、g19），
  其余是台式机主板：没有远程管理，内存多为 31G，PCIe 插槽很少。
- **身份靠 NIS。** 这是历史遗留下来的。home 是 `192.168.50.229:/home/nis` 上的 NFS。
  所有节点上 uid 一致，这是 NIS 目前唯一还在提供的价值。
- **没有调度。** 用卡靠口头约定，比如「g9 的 0–2 卡归别人」。

## 2. 目标

1. 数据和产物不绑在某一台机器上：任何节点都能读到自己的数据，换节点跑作业不需要搬数据。
2. 用卡有排队、有公平、有隔离，不靠口头约定。
3. 权限（谁能用、能用多少、谁能管）写在一个地方，改动有记录。
4. 一个人运维得过来。能用简单方案就不上复杂方案。

## 3. 网络

**倾向：数据网和管理网分开，按节点的量级给不同的速率。** 每类节点给多少、为什么，见 [tiers.md](../ref/tiers.md)；
各档怎么把交换机和网卡买齐，也在那里。

- g8 和 g9 的 X722 是 10GBASE-T 电口，也就是普通网线。它们现在的 10G 口连的是什么，**待定**。

## 4. 存储

**倾向：计算和存储分离。计算节点的本地盘只当临时缓存。**

| 层 | 放什么 | 位置 | 规则 |
| --- | --- | --- | --- |
| `/home` | 代码、环境、配置 | 存储节点，NFS | 每人设配额，做快照 |
| `/project/<组>` | 数据集、checkpoint、实验产物 | 热存储节点，NFS | 按组设配额，做快照，并复制到冷存储 |
| 对象存储 | 封好以后不再改的数据集 | 存储节点 | 可选；你们已经在用 S3 协议 |
| `/scratch` | 训练时读的本地缓存 | GPU 节点本地 NVMe | 自动清理，不备份 |
| 归档与备份 | 冷数据，以及 `/project` 的快照副本 | 冷存储节点，机械盘 | 大容量、便宜 |

- **文件系统，倾向 ZFS + NFS。** 快照、压缩、校验都是自带的，`zfs send` 就能复制到另一台，一个人能运维。
  备选是 BeeGFS 或 CephFS：能横向扩展，但运维重得多。等存储节点超过三台、
  或者单台的带宽顶到上限了，再考虑。
- **容量**按 inventory 里 `/data*` 的已用量，加上两三年的增长来定。
  热存储装正在用的那部分；冷存储装全部数据，再加快照副本。
- **迁移方式**：先把所有本地数据全量冻结到冷存储，再统一整改，最后由每个人在冷存储上决定留还是删。
  路线见 [migration.md](migration.md)。
- 哪些数据在读取量上是大头、要不要做本地缓存，**待定**，需要先向成员了解他们的数据规模。

## 5. 身份与登录

**倾向：用 FreeIPA 替换 NIS。**

- FreeIPA 把 LDAP 目录、Kerberos 认证、按主机限制谁能登录、sudo 规则都集中在一处，
  两台控制节点互为副本，节点上用 SSSD 接入。备选是 OpenLDAP 加 SSSD：更轻，但按主机限制登录和 sudo 规则要自己拼。
- **uid 和 gid 原样迁移**（比如 tianchi.liu 仍然是 1165）。各块盘上已有文件的属主都记的是数字 uid，
  换了号，这些文件就全部错乱了。
- NIS 与 FreeIPA 并行一段时间，逐台节点把 SSSD 切过去，最后再停 NIS。

## 6. 两台控制节点

两台控制节点承担：slurmctld（主备）、slurmdbd 和 MariaDB、身份服务（两台互为副本）、登录入口。

**家目录放在哪，待定：**

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| A. 放在两台控制节点上 | 不用等存储节点 | 两台机器之间做 NFS 高可用要上 DRBD 加 Pacemaker，是整套里最容易出事的部分；控制节点既管调度又扛 IO |
| B. 放在存储节点上，控制节点只跑服务 | 控制节点几乎不存数据，坏了就重装；家目录跟着存储节点的快照和复制走 | 存储节点成为全实验室的单点，需要冷存储做备份 |

目前倾向 B：家目录真正需要的是「坏了能恢复」，快照复制比高可用简单得多。
如果存储节点来得比控制节点晚，可以先用 A 过渡，只做单机 NFS 加定期复制，不上高可用。

## 7. Slurm

这一节的数都是开跑时的初值，由实验室成员商量后调整。

### 组件

- 全集群所有节点跑同一个 Slurm 版本，用上游 tarball 自带的 `debian/` 自己打包，
  22.04 和 20.04 各出一套，都带 NVML 插件。升级顺序是 slurmdbd → slurmctld → slurmd → 客户端。
- 开 configless 模式：只有控制节点上有 `slurm.conf`，计算节点只需要知道控制器地址。
- munge key 全集群共用一把，时钟由 chrony 同步。

### 分区与 GPU

GPU 用 GRES 声明（`AutoDetect=nvml`），型号作为 type，比如 `3080ti`、`3090`、`4090`、`5880ada`；
显存档位写成 Feature，比如 `vram12g`、`vram24g`、`vram48g`。

| 分区 | 用途 | 抢占 |
| --- | --- | --- |
| `gpu`（默认） | 日常训练 | 不被抢 |
| `debug` | 调试、交互 | 不被抢，优先级最高 |
| `scavenge` | 用空闲卡跑可中断的作业 | 被其他分区抢占，抢占后重新排队 |
| `own-<组>` | 某个组出资购买的节点 | 抢占 `scavenge` |

- 用 `select/cons_tres` 分开记账 CPU、内存和 GPU。`DefCpuPerGPU`、`DefMemPerGPU` 按节点组分别设：
  台式机是 12–24 线程配 2 卡，g18 是 208 线程配 8 卡，比例差得太多，不能用一个值。
- Slurm 最小只能按整台节点划分，没法把单独某几张卡划给某个人。
  所以卡的归属改成节点主人享有优先权：主人的作业走 `own-<组>` 分区；其他人只能用 `scavenge` 借这台节点的空闲卡，主人的作业一来，借用的作业就被挤掉、重新排队。

### QOS 与优先级

按公平份额排队（`priority/multifactor`），历史用量的半衰期为 7 天。

| QOS | 单作业最长 | 每人同时占用 | 备注 |
| --- | --- | --- | --- |
| `normal` | 3 天 | 8 卡 | 默认 |
| `debug` | 4 小时 | 1 卡，1 个作业 | 优先级加成 |
| `long` | 14 天 | 2 卡 | 按人授予 |
| `scavenge` | 3 天 | 不限 | 可被抢占 |

### 权限

- **身份**：Slurm 不另建用户，直接用目录服务里的 uid（见第 5 节）。
- **账户树**：slurmdbd 里「account（组）→ user」两级，开启
  `AccountingStorageEnforce=associations,limits,qos,safe`，没被加进任何组的人提交不了作业。
  账户树、各人的 QOS、各组的份额在本仓用声明式文件写，脚本只把差异通过 `sacctmgr` 应用上去，改权限走 PR。
- **管理角色**：

| 角色 | 谁 | 能做什么 |
| --- | --- | --- |
| Slurm 管理员 | 你和实验室管理员 | 改配置、改账户、操作任何作业 |
| 协管员（Operator） | 每组一人 | hold/release、requeue、把节点置为 drain/resume |
| 组协调人（coordinator） | 组负责人 | 在本组内加人删人、调组内限额 |
| 普通成员 | 其他所有人 | 提交、查看、取消自己的作业 |

  sudo 只给要在节点上装包、改系统文件的人，日常调度管理都不需要 root。
- **节点上的执行边界**：
  - cgroup v2 限制设备、CPU 和内存，作业只看得到分给它的卡。
  - pam_slurm_adopt（`PrologFlags=contain`）：在一台节点上没有作业的人 ssh 不进去；有作业的人 ssh 进去后，会话被收进那个作业里。
    管理员组不受限制。sshd 的 PAM 栈里要去掉 `pam_systemd`。
  - docker 组等于 root，能绕开所有限制。接入 Slurm 的节点上，容器改用 Apptainer。
    目前哪些节点装了 docker，见 inventory 的「系统与软件」。

### 按整节点、分阶段接入

一台节点要么完全由 Slurm 管，要么完全不接入。同一张卡上如果既有调度分配的作业、又有绕过调度直接跑的进程，
调度出来的分配就不可信。按整节点接入也方便逐台回退。
先接大节点（卡多，调度的好处最明显），再接台式机。

## 8. 成员的日常作业流

| 场景 | 以前 | 用 Slurm 之后 |
| --- | --- | --- |
| 跑一次训练 | ssh 到节点，看 `nvidia-smi` 找空卡，`nohup python ...` | 在登录节点 `sbatch train.sh`，脚本里写 `#SBATCH --gres=gpu:1` |
| 挑型号或显存 | 自己记住哪台节点是什么卡 | `--gres=gpu:4090:2` 或 `--constraint=vram48g` |
| 调参扫描 | 手写循环，自己轮流分卡 | `sbatch --array=0-19%4` |
| 交互调试 | 直接 ssh 进节点 | `srun -p debug --gres=gpu:1 --pty bash` |
| VS Code / Jupyter | Remote-SSH 直接连节点 | 先 `salloc -p debug ...`，再 Remote-SSH 连分到的节点 |
| 看队列、看用量 | 在群里问 | `squeue --me`、`sacct`、`sshare` |

这套流程适合实验室日常使用。代价是：交互使用要先 `salloc`（高优先级的 `debug` 分区让这一步几乎不用排队）；
用 docker 的人要改用 Apptainer。数据仍锁在本地盘上的作业只能绑定到那台节点，要等第 4 节的存储落地才能解开。

## 9. 采购

按预算分三档，每档累加上一档，见 [tiers.md](../ref/tiers.md)。目前倾向先买档 1（冷存储加网络），冷存储用利旧起步：
没有冷存储，本地盘上的数据就没有地方落脚，整改也就无从开始；冷存储到了后面几档也还用得上。
